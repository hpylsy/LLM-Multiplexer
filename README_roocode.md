## 1. RooCode 是什么

RooCode 是一个运行在 VS Code 中的 AI 编程助手。它不像普通聊天机器人只会回答问题，而是可以在你的授权下：

1. 阅读项目文件。
2. 搜索代码。
3. 修改代码。
4. 创建新文件。
5. 执行终端命令。
6. 分析报错日志。
7. 生成文档、测试、脚本。
8. 使用外部工具，例如 MCP Server。
9. 使用 Skill 执行特定领域的标准化流程。

你可以把 RooCode 理解成一个“会解释、会写代码、会跑命令、会查项目结构”的 AI 助教。但它不是万能的，它需要你给出清晰目标、范围、约束和验收标准。

## 2. RooCode 适合做什么，不适合做什么

### 2.1 适合做的事情

RooCode 特别适合：

- 解释陌生代码。
- 根据需求实现功能。
- 修复 Bug。
- 生成 README、接口文档、部署文档。
- 写单元测试、集成测试。
- 重构重复代码。
- 根据报错日志定位问题。
- 比较两个方案的优缺点。
- 生成数据库模型、API、前端页面。
- 迁移旧代码到新框架。
- 帮助你学习项目结构。

### 2.2 不适合直接交给它的事情

RooCode 不适合被当作“全自动代写机器”：

- 不要让它一次性“完成整个大项目”。
- 不要让它在没有需求说明的情况下自由发挥。
- 不要盲目接受它的所有代码修改。
- 不要把隐私数据、密钥、账号密码直接发给模型。
- 不要让它替代你理解代码、理解作业要求。
- 不要把 AI 生成内容原样当作课程作业提交，除非课程明确允许。

正确的态度是：你是负责人，RooCode 是高级助教。你负责目标和判断，它负责加速执行。

## 3. 第一次使用 RooCode：基本工作流

### 3.1 打开项目

先用 VS Code 打开你的项目文件夹。RooCode 会根据当前工作区理解项目结构。

建议：

1. 只打开当前要处理的项目。
2. 关闭无关大文件，例如日志、PDF、数据集、大型 JSON。
3. 确保项目能在本地正常运行。

### 3.2 选择合适模式

RooCode 通常会提供不同模式，例如：

- Ask：问问题、解释概念，不修改代码。
- Code：写代码、改文件、实现功能。
- Debug：排查错误、定位 Bug。
- Architect：做架构设计、方案规划。
- Orchestrator：拆分复杂任务，多阶段协调。

如果你只是想理解代码，用 Ask。  
如果你要它修改文件，用 Code。  
如果你遇到报错，用 Debug。  
如果你还没想清楚怎么做，用 Architect。

### 3.3 给出任务

一个好的任务应该包含：

1. 背景：这个项目是什么。
2. 目标：你希望实现什么。
3. 范围：只改哪些文件或模块。
4. 约束：不要做什么。
5. 验收标准：怎样算完成。

示例：

```text
请帮我在用户登录页面增加“忘记密码”入口。

背景：这是一个 Django 项目。
范围：只修改登录模板和必要的 URL，不要改数据库模型。
要求：按钮放在登录表单下方，样式与现有页面保持一致。
验收：页面能正常渲染，不影响原有登录功能。
```

## 4. RooCode 的模式：Ask、Code、Debug、Architect、Orchestrator

### 4.1 Ask 模式

适合：学习、解释、比较方案。

你可以问：

```text
请解释这个项目的目录结构，每个模块大概负责什么。
```

```text
请用适合大一学生的语言解释 MVC 和 MTV 的区别。
```

Ask 模式通常不应该修改文件。

### 4.2 Code 模式

适合：真正改代码、加功能、写文档。

你可以说：

```text
请实现一个导出 CSV 的功能，只修改 usage 模块相关文件，并在完成后说明改了哪些地方。
```

Code 模式下，RooCode 可能会读取文件、生成补丁、运行测试。

### 4.3 Debug 模式

适合：有错误、有异常、有测试失败。

你应该提供：

1. 你做了什么操作。
2. 期望结果。
3. 实际结果。
4. 报错信息。
5. 最近修改过什么。

示例：

```text
我运行 python manage.py migrate 后报错，错误如下：...
请先分析可能原因，不要直接改代码。确认原因后再给修复方案。
```

### 4.4 Architect 模式

适合：设计方案、拆任务、评估架构。

示例：

```text
我想给系统增加积分排行榜功能。请先设计数据模型、接口、页面和后台管理方案，不要写代码。
```

### 4.5 Orchestrator 模式

适合：复杂任务，需要拆成多个阶段。

示例：

```text
请把“用户管理 + 权限控制 + 操作日志”拆成多个子任务，先规划，再逐步实施。
```

## 5. 如何有效提问：从模糊需求到可执行任务

### 5.1 不好的提问

```text
帮我改一下页面。
```

问题：

- 不知道哪个页面。
- 不知道改什么。
- 不知道风格要求。
- 不知道是否允许改后端。
- 不知道怎样算完成。

### 5.2 好的提问

```text
请修改个人资料页面，让它更适合手机端显示。

范围：只修改 templates/users/profile.html 和 static/css/site.css。
要求：
1. 手机端卡片宽度占满屏幕。
2. 表单输入框上下排列。
3. 不影响桌面端布局。
4. 不引入新的 CSS 框架。

完成后请说明修改点，并告诉我如何验证。
```

### 5.3 高效提问公式

推荐公式：

```text
你要扮演的角色 + 项目背景 + 具体目标 + 修改范围 + 限制条件 + 输出格式 + 验收标准
```

示例：

```text
你是 Django 后端工程师。
当前项目已有用户、额度、用量记录模块。
请帮我增加“管理员导入用量记录”的错误提示优化。

范围：只检查 usage 模块和对应模板。
限制：不要修改数据库模型；不要改变现有导入格式。
输出：先说明方案，再修改代码，最后给出测试方法。
验收：上传格式错误时，页面能显示具体错误行号和原因。
```

## 6. 高质量提示词模板

### 6.1 解释代码模板

```text
请解释这个模块的作用。

要求：
1. 先用一句话总结。
2. 再按函数/类解释。
3. 说明数据流从哪里来、到哪里去。
4. 指出可能的风险点。
5. 用适合初学者的语言解释。
```

### 6.2 修改代码模板

```text
请实现以下功能：...

背景：...
范围：只修改 ...
限制：不要修改 ...
风格：保持与现有代码一致。
验收：...

请先阅读相关文件，提出简短计划，确认后再修改。
```

### 6.3 调试模板

```text
我遇到了一个错误，请帮我排查。

操作步骤：
1. ...
2. ...

期望结果：...
实际结果：...
错误信息：...
最近修改：...

要求：
1. 先判断最可能的 3 个原因。
2. 再说明如何验证。
3. 最后给出最小修改方案。
```

### 6.4 代码审查模板

```text
请对这次改动做代码审查。

重点检查：
1. 是否有安全问题。
2. 是否有性能问题。
3. 是否破坏现有功能。
4. 是否符合项目风格。
5. 是否需要补充测试。

请按“严重问题 / 建议优化 / 可以接受”分类输出。
```

### 6.5 写测试模板

```text
请为这个功能补充测试。

要求：
1. 覆盖正常场景。
2. 覆盖异常输入。
3. 覆盖权限不足。
4. 测试命名清晰。
5. 不依赖外部网络。
```

### 6.6 写文档模板

```text
请为这个功能写一份学生能看懂的使用文档。

要求：
1. 包含功能简介。
2. 包含操作步骤。
3. 包含常见错误。
4. 包含截图位置说明。
5. 用 Markdown 输出。
```

## 7. Token、上下文窗口与延迟：为什么越聊越慢

### 7.1 什么是 Token

Token 可以粗略理解为模型处理文本的最小单位。中文、英文、符号、代码都会被切成 token。

在 RooCode 中，消耗 token 的内容包括：

1. 你输入的问题。
2. AI 的回答。
3. 系统提示词。
4. 工具说明。
5. 当前项目文件列表。
6. 打开的文件标签页。
7. 被读取的代码文件。
8. 终端输出。
9. 历史对话。
10. 错误日志、文档、数据内容。

### 7.2 什么是上下文窗口

上下文窗口就是模型一次请求最多能“看到”的 token 数。

如果上下文窗口是 128k，表示模型最多能在一次请求中处理约 128k token 的输入和输出。更大的上下文可以让模型记住更多内容，但也会更慢、更贵。

### 7.3 为什么上下文越大延迟越高

原因包括：

1. 模型要读取更多输入。
2. 注意力计算成本更高。
3. 请求体更大，网络上传更慢。
4. 中转服务需要更多时间记录、转发和统计。
5. 缓存命中率可能下降。
6. 接近上下文上限时，服务端调度压力更大。

一个典型现象：

- 8k token 请求可能几秒返回。
- 100k token 请求可能十几秒。
- 300k 到 400k token 请求可能几十秒甚至更久。

所以，“上下文越大越好”是错误理解。正确做法是：只给模型完成任务所需的最小上下文。

### 7.4 输入 token 和输出 token 的区别

输入 token：你发给模型的内容。  
输出 token：模型生成的回答。

很多同学只关注输出长度，却忽略输入长度。RooCode 的慢，很多时候不是因为它回答太长，而是每次请求都带了大量项目上下文。

## 8. 如何节省 Token：不浪费上下文的工程习惯

### 8.1 关闭无关文件

RooCode 可能会参考你当前打开的标签页。打开太多文件，会增加上下文噪音。

建议：

- 当前只处理登录页，就只打开登录页相关文件。
- 不要同时打开大型 README、PDF、日志文件、数据文件。
- 任务结束后关闭无关标签。

### 8.2 新任务开新会话

长对话会积累历史。一个任务完成后，建议开新会话。

旧会话适合继续同一个功能；新会话适合开始新功能。

### 8.3 明确限制读取范围

你可以直接告诉 RooCode：

```text
只查看 users 模块相关文件，不要扫描整个项目。
```

```text
只修改前端模板，不要改后端逻辑。
```

```text
不要读取 PDF 和图片文件。
```

### 8.4 先搜索，再读取

高效方式：

1. 先让 RooCode 搜索关键词。
2. 再读取命中的少量文件。
3. 最后修改相关片段。

低效方式：

1. 让 RooCode 读取整个项目。
2. 让它总结所有文件。
3. 再从中找一个小问题。

### 8.5 不要粘贴超长日志

只贴关键部分：

- 报错类型。
- Traceback 最后 30 到 80 行。
- 触发命令。
- 最近改动。

不要直接贴几千行日志。

### 8.6 让输出短一点

如果只是要改代码，可以要求：

```text
回答请简洁，只说明必要修改点和验证方法。
```

如果是教材、文档、报告，再要求详细。

### 8.7 避免一次性大任务

不要这样问：

```text
请完整分析我的项目并优化所有问题。
```

应该拆成：

1. 分析登录模块。
2. 修复登录问题。
3. 分析权限模块。
4. 优化数据库查询。
5. 补充测试。

### 8.8 使用合适的上下文上限

建议：

| 场景 | 推荐上下文 |
|---|---:|
| 简单问答 | 8k 到 32k |
| 单文件修改 | 16k 到 64k |
| 小模块开发 | 64k 到 128k |
| 多文件重构 | 128k 到 256k |
| 全项目分析 | 256k 以上，谨慎使用 |

## 9. 文件、终端、工具调用：RooCode 是如何工作的

RooCode 不是凭空知道你的项目，它需要通过工具获得信息。

常见工具能力包括：

1. 列出文件目录。
2. 读取文件内容。
3. 搜索关键词。
4. 应用补丁修改文件。
5. 执行命令。
6. 请求你补充信息。

### 9.1 工具调用需要授权

RooCode 通常会在修改文件、运行命令前请求确认。你应该认真看清楚它准备做什么。

尤其注意：

- 是否会删除文件。
- 是否会安装依赖。
- 是否会执行数据库迁移。
- 是否会访问网络。
- 是否会运行危险命令。

### 9.2 让 RooCode 先解释命令

你可以要求：

```text
执行任何命令前，请先说明命令作用和风险。
```

### 9.3 不要盲目运行命令

危险命令示例：

```bash
rm -rf /
```

```bash
git reset --hard
```

```bash
docker system prune -a
```

这些命令可能导致数据丢失。即使 AI 建议，也要先理解再执行。

## 10. Skill：把复杂能力封装成可复用教程/流程

### 10.1 Skill 是什么

Skill 可以理解成 RooCode 的“专项技能包”或“操作手册”。

它通常包含：

1. 某类任务的标准流程。
2. 需要遵守的约束。
3. 推荐使用的工具。
4. 输出格式。
5. 注意事项。

例如：

- 创建 MCP Server 的 Skill。
- 创建自定义模式的 Skill。
- 写部署文档的 Skill。
- 做安全审计的 Skill。
- 生成课程讲义的 Skill。

### 10.2 Skill 解决什么问题

没有 Skill 时，你每次都要告诉 AI：

- 该怎么做。
- 步骤是什么。
- 文件放哪里。
- 输出格式是什么。
- 注意哪些坑。

有 Skill 后，这些流程可以复用，减少重复提示词，提高稳定性。

### 10.3 Skill 的使用场景

适合使用 Skill 的任务：

1. 经常重复做。
2. 步骤比较固定。
3. 需要遵守严格规范。
4. 涉及多个文件或工具。
5. 希望不同同学执行结果一致。

例如课程中可以设计：

- “Django 作业检查 Skill”。
- “实验报告生成 Skill”。
- “代码注释规范化 Skill”。
- “单元测试补全 Skill”。

### 10.4 如何向 RooCode 请求使用 Skill

你可以说：

```text
请使用适合的 Skill 来完成这个任务，并先说明该 Skill 的流程。
```

或者：

```text
如果当前环境有创建 MCP Server 的 Skill，请加载该 Skill，并按照它的步骤执行。
```

### 10.5 如何设计一个好的 Skill

一个好的 Skill 应包含：

1. 名称：清楚说明用途。
2. 适用场景：什么时候用。
3. 输入要求：用户需要提供什么。
4. 标准流程：一步一步做什么。
5. 工具使用规则：什么时候读文件、什么时候执行命令。
6. 输出格式：最后交付什么。
7. 风险提示：哪些操作要谨慎。
8. 示例：给用户参考。

### 10.6 Skill 示例：代码审查 Skill

```text
名称：student-code-review

适用场景：学生提交课程项目后，检查代码质量。

输入要求：
1. 项目语言和框架。
2. 本次改动范围。
3. 作业要求或验收标准。

流程：
1. 阅读项目结构。
2. 识别关键文件。
3. 检查安全问题。
4. 检查代码风格。
5. 检查是否满足作业要求。
6. 给出可执行修改建议。

输出格式：
1. 总体评价。
2. 严重问题。
3. 一般问题。
4. 优化建议。
5. 推荐下一步。
```

### 10.7 Skill 与普通提示词的区别

| 项目 | 普通提示词 | Skill |
|---|---|---|
| 是否可复用 | 较弱 | 强 |
| 是否流程化 | 取决于你怎么写 | 通常流程明确 |
| 适合简单问题 | 适合 | 不一定需要 |
| 适合复杂任务 | 容易遗漏 | 更稳定 |
| 学生统一规范 | 较难 | 更容易 |

## 11. MCP：让 RooCode 连接外部工具和数据源

### 11.1 MCP 是什么

MCP 全称是 Model Context Protocol，可以理解成“让 AI 助手连接外部工具的标准协议”。

普通 RooCode 主要能看到当前项目和终端。通过 MCP，它可以连接更多外部能力，例如：

- 数据库。
- 浏览器。
- GitHub。
- 文件系统。
- 文档库。
- 搜索服务。
- API 服务。
- 内部业务系统。

### 11.2 为什么需要 MCP

没有 MCP 时，AI 想查询外部信息通常只能靠你复制粘贴。

有 MCP 后，AI 可以通过受控工具访问外部资源。例如：

- 查询数据库表结构。
- 读取设计文档。
- 获取 GitHub Issue。
- 调用测试环境 API。
- 检查网页元素。

### 11.3 MCP Server 是什么

MCP Server 是一个提供工具能力的小服务。RooCode 作为客户端连接它，然后调用它暴露的工具。

类比：

- RooCode：学生助教。
- MCP Server：实验室工具箱。
- MCP Tool：工具箱里的螺丝刀、万用表、显微镜。

### 11.4 常见 MCP 类型

| MCP 类型 | 用途 |
|---|---|
| Filesystem MCP | 访问指定目录文件 |
| GitHub MCP | 查看 Issue、PR、仓库信息 |
| Database MCP | 查询数据库结构和数据 |
| Browser MCP | 控制浏览器、检查页面 |
| API MCP | 调用业务接口 |
| Docs MCP | 查询内部文档或知识库 |

### 11.5 使用 MCP 的安全原则

MCP 很强大，也要谨慎：

1. 只连接可信 MCP Server。
2. 不给 MCP 过大的权限。
3. 数据库 MCP 尽量只读。
4. 不把生产环境密钥暴露给学生。
5. 不允许 AI 随意删除数据。
6. 审查 MCP 工具调用日志。
7. 对危险操作设置人工确认。

### 11.6 学生什么时候需要 MCP

一般课程入门阶段，不一定需要 MCP。以下场景才建议使用：

- 需要 AI 查询数据库。
- 需要 AI 操作浏览器做自动化测试。
- 需要 AI 读取课程知识库。
- 需要 AI 分析 GitHub Issue。
- 需要 AI 调用某个内部 API。

### 11.7 如何向 RooCode 描述 MCP 需求

示例：

```text
我想让 RooCode 查询本地 PostgreSQL 数据库的表结构。
请先说明需要什么 MCP Server、权限范围和安全注意事项，不要直接连接生产库。
```

示例：

```text
我希望用浏览器 MCP 检查登录页面的响应式布局。
请只访问本地开发地址，不要访问外部网站。
```

### 11.8 MCP 与直接给 AI 粘贴数据的区别

| 方式 | 优点 | 缺点 |
|---|---|---|
| 手动粘贴 | 简单、可控 | 容易太长、容易泄露、不可复用 |
| MCP | 自动化、结构化、可复用 | 配置复杂、需要权限管理 |

### 11.9 MCP 最佳实践

1. 从只读工具开始。
2. 先在测试环境使用。
3. 每个 MCP 只给必要权限。
4. 给工具起清晰名称。
5. 明确告诉 AI 何时可以调用工具。
6. 对写操作要求人工确认。
7. 不要把密钥写进聊天记录。

## 12. 使用 RooCode 做真实开发任务的标准流程

推荐流程：

### 第一步：说明目标

```text
我要实现一个功能：管理员可以查看每个用户本月 API 使用量。
```

### 第二步：限定范围

```text
请只检查 dashboard 和 usage 模块，不要修改用户认证逻辑。
```

### 第三步：让 RooCode 先读项目

```text
请先阅读相关文件，告诉我当前实现方式和你计划修改的文件。
```

### 第四步：确认方案

你要看它的计划是否合理。如果不合理，及时纠正。

### 第五步：实施修改

```text
按刚才方案修改代码。
```

### 第六步：运行测试或检查

```text
请运行相关测试，或者告诉我应该运行哪些命令验证。
```

### 第七步：总结改动

```text
请总结本次修改的文件、功能点和验证方法。
```

## 13. 调试与排错：如何让 AI 帮你定位问题

### 13.1 提供完整但不冗余的信息

你应该提供：

1. 命令。
2. 报错。
3. 触发步骤。
4. 最近修改。
5. 期望行为。

不要只说：

```text
它报错了，帮我看看。
```

### 13.2 Debug 提问模板

```text
我在运行以下命令时报错：

命令：...
错误：...

我刚刚修改了：...
期望结果：...
实际结果：...

请先分析原因，不要立即改代码。请按可能性排序，并说明每个原因如何验证。
```

### 13.3 让 AI 做最小修复

调试时不要让 AI 顺手重构全项目。应该要求：

```text
请给出最小修改方案，避免影响其他功能。
```

### 13.4 常见排错任务

- 依赖安装失败。
- 数据库迁移失败。
- 页面 500 错误。
- 静态文件加载失败。
- 权限判断错误。
- 表单提交失败。
- API 返回格式不对。
- Docker 启动失败。

## 14. 代码审查、重构与测试

### 14.1 让 RooCode 做代码审查

提示词：

```text
请审查当前功能实现。
重点关注：安全、性能、可维护性、异常处理、权限控制。
不要直接修改代码，先输出问题清单。
```

### 14.2 让 RooCode 做重构

重构不是改变功能，而是改善结构。

提示词：

```text
请重构这段代码，要求功能行为完全不变。
请先说明当前问题，再给出小步重构方案。
每次只做一个小改动，并说明如何验证没有破坏功能。
```

### 14.3 让 RooCode 写测试

提示词：

```text
请为这个功能补充测试。
要求覆盖：正常输入、异常输入、权限不足、边界情况。
测试应能在本地独立运行，不依赖外部网络。
```

### 14.4 测试不是形式主义

AI 写的代码可能看起来正确，但存在隐藏问题。测试可以帮你发现：

- 边界情况没处理。
- 权限绕过。
- 数据为空时报错。
- 时间格式错误。
- 数据库查询过慢。

## 15. 学生常见错误与反例

### 15.1 错误一：需求太模糊

错误：

```text
帮我优化一下。
```

改进：

```text
请优化首页加载速度，重点检查图片体积和数据库查询，不要改变页面布局。
```

### 15.2 错误二：一次要求太多

错误：

```text
帮我把项目做完，包括登录、注册、后台、数据库、部署、测试。
```

改进：

```text
先帮我设计用户登录和注册模块的数据模型与页面流程，不写代码。
```

### 15.3 错误三：不看 AI 的修改

AI 可能会误解需求、改错文件、引入新 Bug。你必须审查它的修改。

### 15.4 错误四：把密钥发给 AI

不要发送：

- API Key。
- 数据库密码。
- Cookie。
- Token。
- 私钥。
- 真实用户隐私数据。

### 15.5 错误五：让 AI 读太多无关内容

错误：

```text
请读取整个项目，然后帮我改一个按钮颜色。
```

改进：

```text
请只查看按钮所在模板和 CSS 文件，帮我把提交按钮改成蓝色。
```

## 16. 课程作业/项目协作中的使用规范

### 16.1 明确 AI 使用边界

课程中建议老师和学生提前约定：

1. 哪些部分允许 AI 辅助。
2. 哪些部分必须学生独立完成。
3. 是否需要注明 AI 使用情况。
4. 是否允许 AI 生成代码。
5. 是否允许 AI 生成报告。

### 16.2 建议提交 AI 使用说明

学生可以在作业中附上：

```text
AI 使用说明：
1. 使用 RooCode 辅助理解项目结构。
2. 使用 RooCode 生成了部分测试样例。
3. 代码由本人审查并修改。
4. 未向 AI 提供隐私数据或密钥。
```

### 16.3 团队协作建议

多人项目中，使用 RooCode 时要注意：

1. 修改前先拉取最新代码。
2. 每次只做一个明确任务。
3. 提交前运行测试。
4. 写清楚 commit message。
5. 不要让 AI 大范围重写队友代码。
6. 重要架构改动先团队讨论。

### 16.4 学术诚信

AI 是学习工具，不是替你学习的工具。你应该能解释自己提交的代码：

- 为什么这样设计。
- 每个函数做什么。
- 出错时如何排查。
- 有哪些边界情况。

如果你无法解释，说明你还没有真正掌握。

## 17. 推荐练习

### 练习 1：解释项目结构

```text
请解释当前项目结构，按模块说明每个目录的作用。要求适合初学者理解，不修改代码。
```

目标：学会用 RooCode 理解项目。

### 练习 2：修改一个小样式

```text
请把登录页面的按钮改得更醒目。只修改登录模板和 CSS，不改后端。
```

目标：学会限定范围。

### 练习 3：排查一个错误

```text
我运行项目时遇到这个错误：...
请先分析原因，不要直接修改代码。
```

目标：学会 Debug 流程。

### 练习 4：写测试

```text
请为用户登录功能设计测试用例，先只输出测试计划，不写代码。
```

目标：学会让 AI 先规划。

### 练习 5：节省 Token

同一个任务分别用两种方式提问：

方式 A：

```text
请分析整个项目，然后帮我修改登录页。
```

方式 B：

```text
请只查看登录页模板和相关 CSS，帮我修改登录按钮样式。
```

比较两次响应速度、上下文大小和结果质量。

## 18. 速查表

### 18.1 任务与模式选择

| 任务 | 推荐模式 |
|---|---|
| 问概念 | Ask |
| 解释代码 | Ask |
| 修改代码 | Code |
| 修 Bug | Debug |
| 设计方案 | Architect |
| 大型任务拆分 | Orchestrator |

### 18.2 高效提示词结构

```text
角色：你是谁。
背景：项目是什么。
目标：我要做什么。
范围：只看/只改哪里。
限制：不要做什么。
输出：按什么格式回答。
验收：怎样算完成。
```

### 18.3 节省 Token 清单

- 关闭无关文件。
- 开新会话处理新任务。
- 限定文件范围。
- 先搜索再读取。
- 不粘贴超长日志。
- 不让 AI 全项目扫描。
- 输出要求简洁。
- 合理设置上下文上限。

### 18.4 安全清单

- 不发密钥。
- 不发真实隐私数据。
- 不盲目执行删除命令。
- 不连接生产数据库做实验。
- 不给 MCP 过大权限。
- AI 修改后必须人工审查。

### 18.5 最推荐的一句话

```text
请先阅读必要文件并提出计划，不要直接修改；范围限定在……；完成后给出验证方法。
```

## 结语

会使用 RooCode，不等于会复制 AI 的答案。真正高效的学生会做到：

1. 把大问题拆成小任务。
2. 给出清晰上下文和约束。
3. 控制 Token 和成本。
4. 审查 AI 的每次修改。
5. 用测试验证结果。
6. 理解代码，而不是只提交代码。
7. 把 Skill 和 MCP 用在真正需要标准化、自动化的场景。

RooCode 的价值不是替代学习，而是把重复劳动、查找资料、模板代码、初步排错这些工作加速，让你把更多时间花在理解、设计和判断上。
